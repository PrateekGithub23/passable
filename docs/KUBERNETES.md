# Running Passable on Kubernetes (kind)

Production runs on Fly.io (see [DEPLOY.md](DEPLOY.md)), where free tiers cover everything. The manifests in `deploy/k8s/` run the same API image on Kubernetes: locally in a [kind](https://kind.sigs.k8s.io/) cluster, and in CI on every push. Nothing here is needed for production. It shows the system running the way it would on a real cluster, with every piece checked.

```sh
scripts/fetch_osm.sh          # once: the OSM extract (data/, git-ignored)
scripts/k8s-up.sh             # cluster, deploy, smoke test (~45 s once images are pulled)
kubectl --context kind-passable -n passable port-forward svc/passable-api 8080:80
kind delete cluster --name passable
```

You need Docker, [kind](https://kind.sigs.k8s.io/), kubectl, Go, curl and jq (`brew install kind` on macOS). Running the script again rebuilds the image and does a rolling restart. The graph is imported only once; `REIMPORT=1` imports it again.

## What gets deployed

```
namespace passable
├── infra/    ConfigMap, Secret, Postgres+PostGIS (StatefulSet + volume), Redis, NetworkPolicies
├── migrate/  Job: /app/migrate (goose). Must complete before the API starts.
└── api/      Deployment (2 replicas), Service, PodDisruptionBudget, ServiceAccount
```

The script applies the three stages in order, the same order as production on Fly: database ready, then migrations (`release_command` there, a Job here), then the API. Between stages 2 and 3 it imports the OSM graph through a port-forward, because each API replica loads the graph from Postgres once at startup.

**Two API replicas** on purpose: each one holds its own in-memory graph and copy-on-write hazard overlay, so a hazard posted to one replica only reaches users connected to the other through Redis pub/sub. The smoke test checks exactly that.

## Design choices

| | Choice | Why |
|---|---|---|
| Probes | **startup** and **readiness** on `/healthz` (which pings Postgres); **liveness** is a TCP check | A replica that can't reach the database is taken out of the Service but not restarted. A liveness check on `/healthz` would restart every replica during a database outage, which fixes nothing. |
| Rollouts | `maxUnavailable: 0`, `maxSurge: 1`; PDB `minAvailable: 1` | A new pod must be ready (graph loaded) before an old one stops. Drains evict one pod at a time. The API handles SIGTERM by finishing in-flight requests (5 s), within the 20 s grace period. |
| Pod security | Non-root (distroless UID 65532), read-only root filesystem, all capabilities dropped, no privilege escalation, `RuntimeDefault` seccomp | Meets the Pod Security "restricted" profile (the namespace warns on violations). The API and Redis comply. The Postgres image needs root to initialise its data directory, which is the one warning you'll see. |
| RBAC | Dedicated ServiceAccount with no Role bindings; token not mounted | The API never calls the Kubernetes API, so a compromised pod gets no cluster credentials. |
| NetworkPolicies | Default-deny ingress; then API ← anyone on 8080, Postgres ← pods labelled `passable/db-client=true`, Redis ← API only | Only the paths the app uses are open. Egress is left open (DNS and nothing sensitive). |
| Resources | Memory requests and limits; a CPU request but no CPU limit | The graph is about 9 MiB of heap. A CPU limit would throttle searches and add latency for no benefit on a shared node. |
| Images | Loaded into the node (`imagePullPolicy: Never`); the PostGIS image is amd64-only, so on Apple Silicon it runs under emulation | No registry needed. The script works around a Docker Desktop export issue with multi-platform images (see the comments in `scripts/k8s-up.sh`). |
| Secrets | Generated by Kustomize from the same throwaway local values as `docker-compose.yml` | A real cluster would use a secret manager (e.g. External Secrets). Production secrets stay in Fly. |

## Verified (local run, Apple M-series, kind v0.33, Kubernetes v1.37)

- **From a fresh cluster to a passing smoke test in 44 s**: 21,173 edges imported, 2 replicas ready, a real wheelchair route from SLC to Hagey Hall (798 m between the two buildings' centre points).
- **Hazard posted to replica A → WebSocket event on replica B:** p50 6.2 ms (4 probes, including the POST's database transaction).
- **Rolling restart** (`scripts/k8s-up.sh` again): new pods became ready before old ones terminated.
- **NetworkPolicies enforced** (tested from throwaway pods):

  | From | To | Result |
  |---|---|---|
  | unlabelled pod | Postgres :5432 | blocked |
  | unlabelled pod | Redis :6379 | blocked |
  | unlabelled pod | API :80 | connected |
  | `passable/db-client=true` pod | Postgres :5432 | connected |
  | `passable/db-client=true` pod | Redis :6379 | blocked |

- **Trivy:** 0 HIGH or CRITICAL vulnerabilities in the API image (distroless base plus two static Go binaries).

## In CI

The `k8s` job in `.github/workflows/ci.yml` builds the image, scans it with Trivy (it fails on any fixable HIGH or CRITICAL vulnerability), then runs `scripts/k8s-up.sh` in a kind cluster on the runner, importing the OSM extract (cached between runs). The Fly deploy waits for this job as well as the tests.
